## 1. 기존 구조와 실제 코드에서 확인한 충돌

기존 Player는 영상 캐시·구간 해시 검사·좌우 독립 재생·파일 재시도·일시 제외·성공 완주 후 복구 기능을 이미 갖고 있다. 해당 동작을 버리고 처음부터 다시 만드는 것이 아니라, 통신·저장·적용 기준을 정리한다.

| 현재 코드·문서 위치 | 기존 동작 또는 충돌 | 최종 변경 |
|---|---|---|
| Player app.js: startOperationIntervals | player-state 15분, notice·black·command 최소 5분, heartbeat 최소 10분, 웹 app-config 최소 30분으로 각각 실행 | 서버 정기 확인을 5분 SyncCoordinator 한 개로 통합 |
| app.js: runImmediateApiBoot, online, visibilitychange | 시작·회선 복구 때 상태·명령·안부·오류 대기열을 따로 호출 | 동일 통신 담당자에게 신호만 전달, 중복 요청 합침 |
| app.js: requestHealthReport | 중요한 상태도 마지막 보고 후 15분을 기다릴 수 있음 | 첫 장애·제외·복구는 중요 이벤트 경로로 우선 전송 |

| Player free-budget.js | player-sync 항목 없음. 알 수 없는 API는 other 하루 20회 | 새 경로·유형별 예산으로 교체. 기존 표에 새 API만 추가하는 방식 금지 |

여기서 “충돌 확인”은 첨부 소스의 정적 대조 결과다. 해결 구현·회귀 시험은 개발자가 수행할 완료 항목이다.

## 2. 변경 구조와 API·저장 계약

### 2-1. 담당을 분리한다

| 담당 | 역할 |
|---|---|
| APP | 기존 WebView·부팅·리모컨·화면 캡처·설정 확인 유지 |
| Player 좌우 재생 담당 | 다운로드·서버 응답을 기다리지 않고 준비된 파일 재생. 좌우 오류와 자원 분리 |
| Player SyncCoordinator | 정기 5분 확인, 중요 이벤트, 재접속·재시도·ACK를 한 통신 대기열로 관리 |
| Player 다운로드 담당 | 별도 취소 가능한 작업. 기본 동시 다운로드 1개. 메타 확인 잠금을 잡지 않음 |
| CMS API | 업체별 버전·제어 전달, 선택적 상태 저장, 게시·명령·사진·백업 |
| D1 | 편집 원본, 작은 게시 포인터, 최신 기기 상태, 제한된 오류 상세, 삭제·명령·용량 예약 장부 |
| R2 | 공유 미디어 원본, 불변 버전 송출표·검사 정보, 비공개 사진·메타 백업 |
| CMS 상태판 | 마지막으로 저장된 상태를 읽음. 보이는 창에서 60초 갱신·수동 새로고침 |

CMS 조회가 평소 상태 저장을 유발하면 안 된다. D1 API를 읽는 횟수와 D1에 쓰는 횟수는 별개다.

### 2-2. /api/player-sync 한 번에서 확인하는 내용

요청 유형은 regular, important, boot, reconnect, result로 구분한다. 중요 보고도 같은 POST 주소를 사용하되 별도 요청 횟수로 계산한다. 필요 없는데 regular 외 요청을 반복하지 않는다.

| 요청에 포함 | 응답에 포함 |
|---|---|
| storeId·appId·웹 설치 ID·지원 기능 | 서버 시각·세션 세대·다음 확인 안내 |
| 서버가 발급한 세대, packetId, sequence | 항목별 ACK·정상 상태 저장 예정 시각 |
| 현재 playerBuild·수신/적용/준비 버전 | 최신 Player release·게시/삭제/선정/제어 버전 |
| 현재 좌우 재생·문제 파일·제외 상태 | 새 목록 또는 변경 문서 안내, 삭제·업체 제외 |
| 누적 오류 요약·전송 대기·축약 여부 | 공지·휴무·블랙모드·명령 |
| 명령·파일 준비·실제 재생 결과 | 명령 유효기간·전달 지연·예산 보호 상태 |

- 같은 버전이면 변경 없음과 작은 상태 정보만 반환. 전체 목록·해시·미디어를 매번 다시 읽지 않음.
- 목록은 현재·예약·공지 정보를 담은 불변 버전 문서. 기본 송출표 R2 읽기는 필요 시 최대 2개로 설계. 추가 문서·HEAD·다운로드는 별도 예산.
- 브라우저 요청은 JSON 내용을 text/plain;charset=UTF-8로 보내 서버가 엄격하게 검증. 불필요한 인증 헤더로 OPTIONS를 만들지 않음. 관리자 API의 인증은 유지.
- 기존 native 업로드에 새 필수 헤더·명령 ID·APP 기능을 요구하지 않음.
- 일반 정기 간격은 300초. 첫 시작·재연결은 0~60초 분산. 늦은 요청 뒤 누락된 정기 호출을 여러 번 몰아서 실행하지 않음.
- 통신 담당자당 API 요청 하나만 진행. 중요 보고는 대기열 앞쪽에 넣으며 큰 미디어 다운로드 완료를 기다리지 않음.
- 세션·설치 ID 대조를 물리 기기에 대한 강한 인증이라고 표현하지 않음.

### 2-3. 5분 확인과 20분 저장

| 시작 후 예시 | 서버 확인 | 정상 상태 D1 쓰기 |
|---|---|---|
| 5분 | 실행 | 없음 |
| 10분 | 실행 | 없음 |
| 15분 | 실행 | 없음 |
| 20분 | 실행 | 1회 |
| 25·30·35분 | 각각 실행 | 없음 |
| 40분 | 실행 | 1회 |

첫 등록·실제 중요 변화는 별도 예외다. 서버의 lastNormalPersistedAt·nextNormalDueAt로 제한한다. 클라이언트 네 번 카운트만 믿지 않는다. 중요 이벤트를 저장해도 정상 20분 시간표를 뒤로 미루지 않는다. HTTP 200, API 수신, D1 저장은 서로 다른 결과다.

평소 최신 상태는 기기당 하나의 runtime_status 행을 기준으로 한다. devices·player_status·통계 테이블에 같은 동적 값을 계속 복제하지 않는다. 기존 devices 화면은 정적 기기 정보와 runtime_status를 합쳐 읽어 호환한다. 정상 영상 시작·종료·프레임·5분 확인마다 원문 INSERT나 last_seen UPDATE 금지.

### 2-4. 사건·요약·세션 계약

| 정보 | 기준 |
|---|---|
| 파일 문제 키 | 웹 설치 ID + left/right + assetId + assetVersion. 파일명만으로 식별하지 않음 |
| 사건 키 | episodeId. 정상 → 새 장애에서 생성, 반복·제외·복구는 같은 사건 |
| 전송 키 | packetId·eventId는 재전송 시 동일. 새 시각으로 바꿔 새 오류처럼 보내지 않음 |
| 누적 횟수 | 사건의 누적 총값과 summaryRevision. 패킷마다 더해 중복 합산하지 않음 |
| 문제 요약 | 첫/최근 시각·총 실패·현재 제외·복구·최근 정상 완주·현재 재생 파일 |
| 정상 상태 시각 | 마지막 일반 저장 시각과 중요 저장 시각을 따로 관리 |
| 서버 현재 상태 | 최신 활성 세대 + 증가 sequence/summaryRevision만 갱신 |
| 과거 오류 | 이력으로 처리. 늦게 온 과거 snapshot으로 현재 정상 상태를 장애로 덮어쓰지 않음 |

서버가 새 세대를 발급하고 새 부팅의 확인 응답 후 활성화한다. 활성 세대 교체는 현재 세대를 조건으로 비교·갱신하여 늦은 옛 등록이 새 세대를 밀어내지 못하게 한다. 재부팅 뒤 로컬 bootSequence가 작다는 이유로 영구 거절하지 않는다. 이전 세대 미전송 오류는 과거 이력으로 구분한다. 같은 웹 설치의 중복 창은 잠금·리더 선출로 정기 호출 하나만 유지한다. 저장소 초기화로 설치 ID가 바뀌면 새 설치로 등록·기기 대응을 확인하며, 임의의 다른 TV 상태를 덮어쓰지 않는다.

ACK는 currentState의 persisted/unchanged/pending_budget/stale/invalid와 상세 eventId의 persisted/suppressed/duplicate를 구분한다. 저장된 summaryRevision과 서버 수신 시각을 반환한다. 저장 확인되지 않은 현재 요약은 대기열에서 제거하지 않는다. 상세 생략 ACK는 “상세 원문 생략”을 뜻하며 장애 해결이나 요약 저장 성공이 아니다.

미전송 상세 대기열은 IndexedDB 중심으로 7일·10MB 초기값. 반복 원문은 합치고 축약 횟수를 보존한다. **현재 미복구 장애 요약과 영구 삭제 원장은 7일 만료로 지우지 않는다.** 다시 연결하면 현재 요약부터 보내고 과거 상세는 제한된 묶음으로 처리한다.


### 2-5. CMS 접속 표시: 선택 A를 기본안으로 확정

**5분 sync 성공과 CMS 온라인 표시는 같은 뜻이 아니다. 기본안은 선택 A이며 10분 last_seen 추가 쓰기를 넣지 않는다.** 무료 플랜에서 넉넉한 쓰기 여유를 유지하는 목적에 맞춘 결정이다. 선택 B는 아래 비용·시험 조건을 만족한 뒤 별도로 전환하는 대안이며 기본 배포에서 켜지 않는다.

TV가 02:00 sync에 성공해도 마지막 D1 저장이 01:45라면 CMS는 01:45 자료를 표시한다. 서버가 요청을 받았다는 사실만으로 D1에 시각·로그·예산 카운터를 따로 쓰지 않는다. TV를 껐을 때 5분 안에 이를 CMS가 확정한다고 약속하지 않는다.

| CMS 접속 표시 | 기본 판정 | 반드시 함께 보여 줄 정보 |
|---|---|---|
| 정상(최근 저장 기준) | 유효한 상태 자료가 있고 마지막 접속 기록의 나이가 20분 이내 | 마지막 접속 기록 시각·상태 자료 시각. 지금 재생을 실시간 보증하지 않음 |
| 상태 오래됨 | 마지막 접속 기록이 20분 초과 ~ 30분 미만 | 최신 상태 확인 대기. 잠깐의 저장 간격·통신 지연일 수 있음 |
| 연결 확인 필요 | 마지막 접속 기록이 30분 이상 | 상태 지연 경고. 전원 꺼짐·인터넷 단절·서버 장애 원인은 미확정 |
| 아직 확인되지 않음 / 조회 실패 | 등록 전이거나 정상 자료가 없거나 CMS의 D1 조회 실패 | 기존 자료가 있으면 유지하되 조회 실패 이유·자료 시각 표시 |

- 기본 자동 목록에 근거 없이 실시간 온라인/오프라인을 단정한 녹색·빨간 표시를 사용하지 않는다. 예전 온라인 기능은 최근 저장 기준의 접속 상태로 유지한다.
- 접속 여부와 LEFT/RIGHT 재생 건강은 별도다. 접속이 최근이어도 영상은 고장날 수 있고, 서버 접속이 오래돼도 캐시 방송은 계속될 수 있다.
- lastContactPersistedAt은 실제로 저장된 정상 상태·중요 요청의 서버 수신 시각을 기준으로 한다. 현재 상태를 갱신하지 못한 옛 세대 패킷·과거 상세·CMS 조회·사진 업로드를 새 Player 접속 증거로 사용하지 않는다.
- left/right 상태에는 해당 상태의 측정·저장 시각을 붙인다. 중요한 한쪽 사건이 접속 시각을 갱신했다고 다른 쪽의 오래된 재생 자료까지 새 자료로 바꾸지 않는다.
- CMS는 서버 시각 기준으로 자료 나이를 계산하고 보이는 창에서 60초마다 표시를 갱신. 수동 새로고침도 저장된 자료를 다시 읽으며 TV의 즉시 응답을 보장하지 않는다.
- TV 전원이 실제 꺼진 뒤 경고까지 수십 분 걸릴 수 있다. 자료가 이미 오래된 경우 더 빨리 보일 수도 있다. 30분은 마지막 기록 기준 경고선이고, 실제 전원 종료 시각을 뜻하지 않는다.
- HTTP 성공·명령 전달·파일 준비·실제 재생·상태 저장·CMS 표시를 각각 구분한다. 선택 A 때문에 첫 오류의 우선 보고를 20분까지 늦추지 않는다.
- 서버 Worker의 메모리에 남은 last_seen을 정확한 기기 상태의 영구 저장소로 사용하지 않는다. R2/KV/DO에 매 sync 흔적을 저장하는 별도 구조도 기본안에 추가하지 않는다.

**선택 B의 정확한 비용과 제약(기본안에서 비활성)**

| 선택 | 평소 기록 | 100대 하루 D1 쓰기 모델 | 정상 목표 50,000행까지 여유 |
|---|---|---:|---:|
| A: 이번 기본안 | 20분 전체 상태, 중간 last_seen 쓰기 없음 | 41,500행 | 8,500행 |
| B: 중간 UPDATE가 실제 1행 | 10분 last_seen만, 20분 전체 상태에 접속 시각 포함 | 48,700행 | 1,300행 |
| B: 중간 UPDATE가 실제 2행 | 색인·트리거·중복 장부 때문에 비용 증가 | 55,900행 | 목표 5,900행 초과 |

추가 작업은 100대 × 하루 72회 = 7,200회다. 20분 전체 저장 때 last_seen을 또 따로 UPDATE하지 않는다. 따라서 실제 중간 작업이 1행이면 41,500 + 7,200 = 48,700행, 2행이면 41,500 + 14,400 = 55,900행이다. 이는 기본값·다른 사용량이 같은 조건의 계산이며 실측 보장값이 아니다.

B를 켜려면 접속 시각을 색인·별도 로그로 중복 갱신하지 않고, 기기 기본키로 한 행을 찾아 서버의 유효 세션·시각 조건으로 중복 쓰기를 막는다. 모든 관련 SQL meta.rows_written을 합산해 실제 1행임을 증명해야 한다. 기기와 서버 모두 10분 저장 시각을 확인하며 재접속했다고 같은 슬롯을 반복 저장하지 않는다. 중간 UPDATE는 전체 상태의 시각·sequence·오류·정상 20분 시간표를 갱신하지 않는다. 실패해도 정상 방송을 정지시키지 않는다.

10분은 접속 기록 간격이지 정확한 오프라인 발견시간이 아니다. 예를 들어 B에서 마지막 접속 기록 15분 경과 후 연결 확인 경고를 띄우면 CMS 조회·지터까지 더해 15~16분 정도 걸릴 수 있다. 서버 장애와 TV 전원 꺼짐도 구분할 수 없다. B를 채택할 때 경고선·지터·허용 최대 지연을 별도 시험으로 확정해야 한다.

B 전환은 실제 계정 쓰기 50,000행/일 이하와 오류·사진·교체·재접속일의 여유를 모두 확인한 경우만 허용한다. 48,700행이라는 계산만으로 전환하지 않는다. 전환 시 아래 읽기 전용 계약의 예외에 10분 last_seen 저장도 명시해야 하며 A와 B를 동시에 켜지 않는다.

### 2-6. 변경 없음 regular sync의 비용 계약

**정상적인 변경 없음 regular sync는 읽기 전용이다. 단, 20분 정상 저장 시각과 실제 중요한 상태변화는 명시적인 예외다.** 모든 5분 요청을 무조건 쓰기 0행이라고 선언하면 20분 기록과 충돌하므로 두 경로를 분명히 나눈다.

아래 조건을 모두 만족한 요청을 read-only regular로 정의한다.

- 유효한 등록·세션이며 boot/reconnect 등록 작업이 아님.
- 게시·삭제·right 선정·공지·휴무·블랙·Player release 버전 변경 없음.
- 새 오류·제외·복구·중요 명령 결과·파일 준비 결과 없음. 단순 누적 횟수 전달만으로 중요 쓰기를 만들지 않음.
- 처리할 새 명령 없음, 정상 20분 저장 시각이 아직 도래하지 않음.
- 선택 A 운영이며 10분 last_seen 쓰기 기능은 꺼져 있음.

| read-only regular 한 번의 실제 비용 | 합격값 |
|---|---:|
| D1 rows_written | **0행** |
| R2 Class A | **0회** |
| R2 미디어 GET/HEAD/Range | **0회** |
| 미디어 재다운로드 | **0개** |
| R2 송출표 GET/HEAD | **0회**: D1의 작은 버전 포인터로 변경 없음 판단 |
| D1 rows_read | 작은 색인 조회만. 기본 경로 평균 5행 이하 설계·실측, 전체 계정 하루 1,000,000행 이하 |

변경 없음이라도 Workers 요청 1회와 소량 D1 읽기는 발생한다. 비용이 완전히 0이라는 뜻이 아니다. 정상 경로는 큰 목록을 만들거나 읽지 않고, 작은 버전·업체 활성·세션·필요 명령 포인터만 확인한다.

| 요청 종류·시각 | 허용된 저장·파일 작업 |
|---|---|
| A의 5·10·15분 변경 없음 | 위 0 비용 계약 적용 |
| A의 20분 변경 없음 | 정상 상태 작업 1회, 최대 3행 가정. R2 A/미디어 GET/재다운로드는 0 |
| 실제 새 중요 변화 | 중요 상태·제한된 표본 저장, 별도 예산·ACK 적용 |
| 최신 버전 변경·새 파일 필요 | 필요한 송출표·신규/교체 파일만 읽기, 기존 원본 재사용 |
| boot·등록·실제 명령 결과 | 목적에 필요한 작업만, 해당 기타 예산으로 계산 |

API middleware·ensureSchema·devices 갱신·접속 로그·sequence 장부·UTC 카운터 초기화·D1 사용량 집계·R2 상태 파일 PUT 때문에 숨어서 쓰는 것도 0 비용 계약 위반이다. 스키마 이행·정리는 배포/제한된 관리 작업에서 수행한다. 계측은 SQL meta·Worker 로그로 하고 계측용 D1 INSERT를 매 요청 붙이지 않는다.

실수로 모든 정기 요청에 별도 1행 쓰기를 더하면 하루 28,800행이 추가되어 기본 41,500 + 28,800 = 70,300행이 된다. 매 요청에 R2 PUT 하나를 붙이면 30일 864,000회, 31일 892,800회가 추가된다. 원래 월 15,060회 운영 예시와 합치면 30일 879,060회로 무료 Class A 1,000,000회의 대부분을 사용한다. 0 비용 계약은 문구만이 아니라 시험에서 확인한다.

### 2-7. Workers Free CPU 10ms 계약

Cloudflare 공식 기준의 HTTP 요청당 CPU time 제한은 **10ms(0.01초)**다. D1/R2/fetch 응답을 기다리는 시간은 CPU time과 다르며, JSON 파싱·생성·정렬·검증·로그·middleware 등 실행 작업은 CPU 비용에 포함된다. 응답까지 걸린 총시간이 100ms라고 CPU 초과인 것도 아니고, 요청 수가 적다고 CPU 제한이 없어지는 것도 아니다.

| 처리 위치 | 허용·금지 기준 |
|---|---|
| regular sync | 작은 버전·업체·세션 조회, 필요한 작은 응답·제한된 요약 처리만 |
| 게시/편집 단계 | 업체별 허용 목록·예약을 미리 계산해 불변 송출표 저장. sync에서 전체 업체 재계산 금지 |
| 미디어 검사 | 기존 CMS 브라우저/관리 도구가 해시 생성, TV가 검사. sync에서 파일 해시 금지 |
| 정리·R2 재고 대조 | 제한된 별도 작업. 전체 R2 스캔을 regular 안에서 실행하지 않음 |

- read-only regular 응답 16KiB 이하, 요청 요약 64KiB 이하를 초기 크기 기준으로 둔다. 본문 크기를 제한하고 작은 고정 응답 형식·색인 조회를 사용한다. 실제 최대 편성으로 CPU·내용 누락을 검증한다.
- 문제 파일이 많아 상한을 넘으면 현재 요약·전체 장애 수·남은 항목 수를 알리고 제한된 묶음으로 나눈다. 항목을 잘라낸 뒤 오류 없음으로 표시하지 않는다. 분할 요청·읽기·쓰기 역시 별도 예산으로 계산한다.
- JSON 전체 목록 만들기·모든 업체 필터·큰 배열 정렬·전체 콘텐츠 순회·파일/대형 문서 해시·전체 R2 스캔을 regular 안에서 실행하지 않는다. 클라이언트 요청 때문에 게시를 자동 재생성하지 않는다.
- 서버가 보낸 큰 R2 문서를 필요 없이 다시 파싱·재조립하지 않는다. 변경이 있는 경로도 필요 문서만 전달하며 동일 CPU 제한을 검증한다.
- **합격: regular CPU p99 5ms 이하를 안전 목표로 하고, 측정한 요청별 CPU 최대 10ms 이내·exceededCpu 0건.** 정상·20분 저장·중요 보고·변경·재접속·콜드 시작·동시 100대 조건을 따로 측정한다.
- 측정은 배포 Worker의 CPU 지표·invocation 로그의 CPU time으로 한다. Date.now/performance.now로 API 응답 전체 시간을 잰 값을 CPU time이라고 제출하지 않는다. 평균만 보고 합격시키지 않고 p95·p99·관측 최대·표본 수·기간·실제 배포 build를 남긴다.
- CPU 제한 초과는 exceededCpu / Exceeded CPU Time Limits로 확인한다. Cloudflare 오류 1102는 메모리 초과도 나타낼 수 있으므로 모든 1102를 CPU 문제라고 단정하지 않는다.
- 로그·관측 작업도 CPU/요청 예산에 포함한다. 별도 유료 Tail/Logpush/DO를 기본 전제로 추가하지 않고 현재 무료 환경에서 제공되는 지표·로그를 우선 사용한다.
- 로컬 시험은 병목 확인용이고 실제 무료 배포의 CPU 증거를 대체하지 못한다. 합격하지 못하면 작은 응답·색인·처리 분리로 보완한 뒤 다시 시험하며 유료 플랜 전환으로 무료 합격을 주장하지 않는다.
- CPU 오류나 서버 실패 때도 마지막 정상 재생·캐시는 보존하고 같은 Coordinator가 재시도를 늦춘다. 장애 응답을 정상 빈 편성으로 적용하지 않는다.

## 3. 실제 동작 순서와 CMS 표시

### 3-1. 평소와 목록 변경

1. APP이 기존 주소의 Player 실행. 마지막 정상 목록·파일을 복구해 먼저 재생.
2. 5분 통합 확인에서 게시·선정·삭제·제어·명령·Player 버전 확인.
3. 20분 정상 저장 시각이 아직 안 됐으면 정상 상태 D1 쓰기 생략.
4. 바뀐 목록이 있으면 완성·업체 대상·버전·형식을 검증하고 최신 목표를 저장.
5. 삭제·대상 제외를 먼저 재생에서 제거. 원본 파일 삭제는 나중에 처리.
6. 기존 파일 재사용, LEFT/RIGHT 첫 파일 우선, 준비된 파일부터 CMS 순서로 사용.
7. 수신·부분 준비·전체 준비·실제 재생을 구분하여 중요 결과 예산으로 보고.
8. 다운로드 중 더 최신 버전이 오면 이전 작업 적용 권한 취소. 완료 시 세대·목표 버전·필요 집합·삭제 원장 재검증.

메타 확인 잠금은 응답 처리 직후 풀고 다운로드는 별도 작업으로 수행한다. 90초짜리 다운로드 여러 개를 기다리느라 다음 5분 확인이 빠지면 불합격이다.

| 변경 예 | 행동 |
|---|---|
| A→B→C에서 C→A→B | 같은 원본·버전이면 재다운로드 0회, 순서만 변경 |
| A→B→C에서 A→D→C→E | A·C 재사용, B 편성 제외, D·E만 다운로드 |
| 같은 콘텐츠의 명시적 교체 | 삭제·기간·업체 대상이 유효한 동일 콘텐츠 이전본만 임시 사용 가능 |
| 위치만 같고 다른 콘텐츠 | 삭제한 B를 새 D의 임시 대체로 사용하지 않음 |
| 명시적인 정상 빈 목록 | 캐시된 기본 화면·설정된 정지 화면. 옛 광고를 계속 틀지 않음 |

### 3-2. left_2.mp4 장애 예시

정상 재생 순서: left_1 → left_2 → left_3. RIGHT는 별도 정상 재생.

| 순서 | Player 행동 | 서버·CMS 행동 |
|---|---|---|
| left_2 첫 실패 | 오류 이벤트에서 즉시 감지, 사건 생성·실패 1회 저장, 우선 보고 | 중요 상태와 첫 상세 표본을 예산 안에서 저장 |
| 약 2초 후 | 해당 파일 한 번 재시도. RIGHT는 유지 | 통신을 기다리며 영상 전체 정지 금지 |
| 재시도도 실패 | 누적 2회, 현재 일시 제외, 제외 전환을 우선 보고 | 현재 일시 제외와 다른 LEFT 재생을 구분 |
| 다음 재생 | left_3 등 준비된 정상 파일 사용 | LEFT 일부 송출 장애 / RIGHT 정상 |
| 이후 재검사 실패 | 횟수·최근 시각만 갱신. 이미 제외 상태라면 새 제외 사건으로 쓰지 않음 | 다음 5분 확인에 누적 요약 수신, 불필요한 상세 반복 생략 |
| left_2 재검사 성공 | 실제 정상 진행·완주 확인 후 해당 사건 복구 보고 | 해당 파일 정상 복구 시각 표시 |
| left_3만 성공 | left_2 문제 유지 | left_2까지 자동 정상 처리 금지 |

- error·decode 실패는 이벤트 발생 시 처리. 시작 실패는 20초, 재생 진행 정지는 15초를 초기 판단값으로 두고 TV 안에서 2초마다 검사한다. 서버 5분 확인을 기다려 오류를 발견하지 않는다.
- 수동 정지·공지·휴무·블랙모드·전환 준비·정상 종료는 고장으로 판단하지 않음.
- 첫 짧은 재시도 후에는 1분 → 5분 → 15분 → 최대 60분으로 복구 확인을 늦추는 초기 정책. 복구 시도 중에도 제외 상태는 유지, 실패할 때마다 제외/정상 상태를 번갈아 기록하지 않음.
- 새 세션에서도 미복구 문제와 재검사 예정 시각 복원. 부팅 때 모든 문제를 정상으로 초기화하지 않음.
- 기본은 정상 캐시로 재검사. 디코딩 문제마다 R2 원본 재다운로드 금지. 손상 증거가 있거나 버전 변경 시 필요한 파일만 다시 받음.
- 영상은 정상 진행 뒤 성공 완주가 복구 증거. 짧은 영상은 정상 종료, 이미지는 지정 시간 정상 표시 완료. 그전에는 복구 확인 중.
- 문제 파일이 영구 삭제·편성 제외되면 대상 해제 상태로 기록. 재생 증거 없이 정상 복구라고 쓰지 않음.
- 한쪽 오류로 양쪽 reload·캐시 전체 삭제·APP 재시작을 자동 실행하지 않음.
- 같은 메인 JS/APP 전체가 멈추면 JS 감시가 스스로 복구한다고 보장하지 않음.

### 3-3. 중요 보고와 예산 한도의 의미

새 장애 → 제외 → 복구를 각각 저장했다면 중요 추가 기록 3회다. “각 종류마다 하루 10회”가 아니다. 같은 패킷에서 여러 변화의 최신 요약을 한 행에 합칠 수 있으나 첫 장애를 다음 5분까지 일부러 기다려 합치지 않는다. 상세 표본 쓰기는 중요 상태 행 쓰기와 별도이며 예산 표에 둘 다 계산한다.

| 조건 | 정책 |
|---|---|
| 새 중요 변화, 기본 예산 남음 | 가능한 즉시 POST. 정상 연결 목표 서버 저장 5초 이내 |
| 같은 사건 반복 | 로컬 합산, 다음 5분 확인에 현재 요약. 단순 횟수 변화만으로 매번 D1 쓰지 않음 |
| 상세 표본 10개 사용 | 새 원문 생략, 현재 문제 요약 유지, 상세 축약 표시 |
| 중요 추가 저장 약 10회 사용 | 즉시 요청 남발 중지·같은 대기열에 합침. 다음 5분 확인에서 현재 문제를 우선 전달 |
| 예산 초과 후 새 제외·복구 | 공용 쓰기 여유에서 현재 상태 갱신을 먼저 처리. 상세·과거 로그·정리는 뒤로 미룸 |
| 쓰기 보호 또는 서버 저장 실패 | pending_budget/실패 ACK, 로컬 요약 유지. CMS는 마지막 저장 상태·시각·지연 표시 |

**41,500행은 기본 예산이고 50,000행은 정상 운영 목표다.** 약 10회를 넘는 중요 변화에는 공용 여유를 사용할 수 있으므로 폭주일 실제 수치는 별도로 계산한다. 비용 제한과 모든 사건의 무제한 즉시 저장을 동시에 약속하지 않는다. 요약은 모든 5분 요청에 전달하지만, 변함없는 장애의 반복 횟수 저장은 20분 정상 슬롯에 합친다. 새 제외·복구는 중요한 상태변화로 먼저 저장한다. 강한 예산 보호 때는 중요 상태 전달·저장도 지연될 수 있으며 이를 오류 없음으로 표시하지 않는다.

CMS가 모르는 미수신 오류를 이미 알고 있다고 주장할 수는 없다. 연결 단절은 마지막 확인 시각을 보여주고, 서버가 확인한 예산 보호·저장 지연은 별도 표시한다.

### 3-4. CMS 화면 예시

| 연세탄탄 TV | 표시 예 |
|---|---|
| LEFT 전체 | 일부 송출 장애 |
| 문제 파일 | left_2.mp4 |
| 현재 파일 상태 | 현재 일시 제외 |
| 최초 오류 | 19:03:12 |
| 최근 오류 | 19:03:20 |
| 사건 실패 횟수 | 2회 |
| 현재 다른 LEFT 콘텐츠 | left_3 정상 재생 중 |
| RIGHT | 정상 재생 중 |
| 이후 동일 파일 성공 완주 | 19:07:24 정상 복구 |
| 상세 한도 초과 | 상세 기록 축약 중 / 현재 장애 요약 유지 |
| 오래된 상태 | 마지막 저장 시각·상태 오래됨·변경 전달 대기 |

기기·좌우·파일의 상태를 따로 표시한다. 다른 LEFT가 정상이어도 고장 파일이 있으면 일부 송출 장애다. RIGHT는 해당 화면의 실제 보고로 판정한다. 복구 이력은 유지하되 현재 장애로 다시 계산하지 않는다.

보이는 CMS 창에서 60초 갱신, 숨긴 창은 일시 중지. 수동 새로고침 가능, 동시에 중복 조회 금지. 5분 Player 확인과 CMS의 60초 조회는 서로 다른 주기다.

접속 표시는 2-5절의 선택 A로 확정한다. 정상(최근 저장 기준) / 상태 오래됨 / 연결 확인 필요를 사용하며, 마지막 저장 후 30분 경고를 전원 꺼짐 확정으로 표시하지 않는다. 게시 버전과 수신/적용 버전이 다르면 변경 전달 대기를 표시하되 자료의 저장 시각을 함께 보여 준다. 5분 실제 sync 성공을 매번 D1에 저장하는 편법을 사용하지 않는다.

| 반영 항목 | 정상 연결·예산 여유 조건의 시험 목표 |
|---|---|
| 새 첫 장애·제외·복구 서버 기록 | 감지 이후 가능한 즉시, 5초 이내 목표 |
| CMS에 새 중요 기록 보임 | 다음 60초 조회까지, 감지 이후 약 65초 이내 목표 |
| 일반 변경·새 명령 발견 | 다음 5분, 초기 분산 포함 6분 이내 목표 |
| 새 미디어 재생 | 위 시간 + 다운로드·검사·전환 시간 |
| 원격 스크린샷 수신 | 명령 수신 후 촬영·저장, 전체 7분 이내 시험 목표 |
| 정기 상태 최신도 | 20분 전 자료일 수 있음. 마지막 상태 저장 시각 표시 |
| 예약 전환 | 시간표·파일 준비 시 30초 이내 |
| 중요 보고 예산 소진 | 다음 5분에 전달, 실제 저장 시각·보호 지연 별도 |

명령 유효기간은 기존 설계의 20분을 유지한다. 지난 재시작·촬영을 재연결 후 몰아서 실행하지 않는다. 위 시각은 인터넷 장애·예산 소진·큰 파일 전송 때 보장하지 않는다.

## 4. D1·R2·Workers 예상 사용량

### 4-1. 무료 한도와 목표

| 항목 | 공식 무료 제공량 | 기본 계산 또는 운영 목표 |
|---|---:|---:|
| Workers·Pages Functions 요청 | 100,000회/일 | 기본 예산 43,600회/일, 정상 목표 50,000회 이하 |
| Workers HTTP CPU time | 10ms/요청 | regular p99 5ms 이하 목표, 관측 최대 10ms 이내, exceededCpu 0건 |
| D1 읽기 | 5,000,000행/일 | 정기 모델 168,000행 + 추가, 전체 목표 1,000,000행 이하 |
| D1 쓰기 | 100,000행/일 | 기본 예산 41,500행, 정상 목표 50,000행 이하 |
| D1 공간 | 계정 전체 5GB, 개별 DB 500MB | 해당 DB 250MB 이하 목표 |
| R2 Standard 공간 | 10GB-month/월 | 평소 5GB 미만 목표, 단계별 보호 |
| R2 Class A | 1,000,000회/월 | 목표 100,000회 이하 |
| R2 Class B | 10,000,000회/월 | 목표 3,000,000회 이하 |

D1 무료 읽기·쓰기는 하루 단위, Workers 일일 한도도 UTC 자정(한국 오전 9시) 기준이다. R2는 월 제공량이며 초과 사용에 과금이 생길 수 있다. Standard만 무료 제공량 적용. 용량은 하루 최대 보관량을 기간 평균하는 GB-month이므로 한 달 계속 5GB를 두면 약 5GB-month다. 같은 계정의 다른 앱·버킷까지 합산한다.

### 4-2. Workers 계산

| 항목 | 계산 | 하루 |
|---|---|---:|
| 5분 player-sync | 100 × 24 × 12 | 28,800회 |
| 기존 native APP 설정 확인 30분 | 100 × 24 × 2 | 4,800회 |
| 기타 예산 | 중요 보고·명령 결과·사진·CMS·미디어·시작·재시도·유지 작업 | 10,000회 |
| 합계 | 33,600 + 10,000 | **43,600회** |
| 공식 한도 대비 여유 | 100,000 - 43,600 | **56,400회, 56.4%** |

중요 이벤트의 즉시 전송은 별도 요청이며 기타 10,000회에 포함한다. 구현용 예산 예시는 Player 추가 작업 3,000회와 비Player 작업 7,000회. 같은 작업을 두 몫에 중복 계산하지 않음. 정적 파일은 Functions를 호출하지 않도록 라우팅한다.

| 조건 변경 | 하루 모델 | 조치 |
|---|---:|---|
| 모든 APP 설정 확인이 10분 | 53,200회 | 현재 설정 실측, APP 변경 대신 선택적 호출부터 축소·목표 재평가 |
| 정기 웹 요청마다 OPTIONS 추가 | 72,400회 | 단순 요청·CORS 수정, 이를 정상 합격 모델로 인정하지 않음 |
| 위 두 조건 동시 | 82,000회 | 기본 여유와 크게 다름. 그대로 100대 확대 금지 |
| 구버전/신버전 동시 운영 | 각 실제 기기 요청 합산 | 전환 기간 별도 계산, 기존 API 유지 비용 반영 |

요청 보호 초기값: TV당 정기·시작 분산 몫 300회, 추가 중요 보고 10회, 시작/명령 등 결과 20회, 추가 재시도 40회 = 370회/일. 예외 상한 모델은 370 × 100 + native 4,800 + 비Player 7,000 = **48,800회/일**. 288회 기본 정기 몫을 부가 작업이 먼저 쓰지 않게 분리한다. 추가 요청을 못 보내도 다음 정기 요약은 유지한다. 정상 상태의 5분 확인을 하루 20회 제한으로 막는 옛 Budget를 사용하지 않는다. 한도 확인·장부 자체의 쓰기와 요청도 실제 예산에 포함한다.

### 4-3. D1 쓰기: 20분 유지

한 상태/표본 작업에 색인·보호 기록까지 최대 3행 쓰기를 가정한 모델이다. SQL·색인을 제한하고 rows_written으로 검증한다. DB로 보낸 SQL 수와 쓰기 행 수를 혼동하지 않는다.

| 항목 | 계산 | 하루 쓰기 |
|---|---|---:|
| 정기 20분 상태 | 100 × 72 × 3 | 21,600행 |
| 중요 상태 추가 | 100 × 약 10 × 3 | 3,000행 |
| 시작·재연결 | 전체 300 × 3 | 900행 |
| 상세 오류 표본 | 100 × 약 10 × 3 | 3,000행 |
| 과거 오류 정리 | 최대 1,000 × 3 | 3,000행 |
| 그 밖의 쓰기 | 사진·명령·선정·콘텐츠·게시·수신/준비/재생 결과·용량 예약 등 | 10,000행 |
| 합계 | — | **41,500행** |
| 공식 무료 한도 대비 여유 | 100,000 - 41,500 | **58,500행, 58.5%** |

30일 예산 1,245,000행, 31일 1,286,500행. 월 합계가 낮아도 특정 하루 한도를 넘으면 제한된다. 오류 하루 약 10회는 예산 기본값이며 추가 변화는 공용 여유와 정상 목표를 함께 검증한다.

**잘못 5분마다 상태를 쓴다면** 정기 상태만 86,400행 + 나머지 19,900행 = **106,300행/일**. 무료 한도를 넘을 수 있으므로 반드시 시험에서 차단한다.

3행 가정 작업이 실제 5행이면 같은 작업 수에서 **62,500행/일** 모델이 된다. 무료 한도 이하여도 50,000행 정상 목표를 넘는다. 색인·중복 행·장부를 줄인 뒤 재검증한다.

선택 A에는 중간 last_seen 쓰기 0회다. 선택 B의 추가 7,200행/일 및 실제 2행이면 목표 초과하는 계산은 2-5절에 별도 명시한다. B는 이번 합계에 포함하지 않는다.

### 4-4. D1 읽기와 공간

기본 정기 요청 33,600회 × 평균 읽기 5행 = **168,000행/일**(30일 5,040,000행, 31일 5,208,000행). 이는 작은 버전·업체·상태를 색인으로 찾는 가정이다. 관리자·추가 보고·예약 편집·기존 APP의 실제 읽기는 합산하며 전체 1,000,000행/일 이하를 목표로 한다.

- 정기 확인마다 전체 콘텐츠·전체 예약·전체 오류·전체 기기를 읽지 않음.
- 상태 행은 최신 1행, 상세 오류 표본은 수신 후 7일, 일별 합계는 30일 기본. 기존 장기 통계는 작은 합계로 보존.
- 활성 미복구 문제·현재 설정·삭제 원장은 나이가 들었다는 이유로 제거하지 않음.
- DB 250MB는 관리 목표. 현재 DB 재고를 보지 않고 실제 보관량이라고 단정하지 않음.
- 보호 카운터는 가능한 기존 상태 행의 UTC 일자·횟수에 합침. 매 5분 요청마다 별도 사용량 행 UPDATE 금지.
- 계정 사용량·행 비용은 분석/응답 meta 중심으로 확인. 계측 자체 SQL도 예산에 포함.

### 4-5. R2 Class B: 모든 확인에 변경이 있다는 보수적 예산

변경 없음 경로의 송출표·미디어 GET/HEAD는 0회다. 아래는 모든 정기 확인에 새 버전이 필요하고 문서 캐시도 도움이 되지 않아 송출표 두 개를 읽는 극단적 경우까지 배정한 예산이다. 이 숫자를 매 sync에서 두 문서를 읽으라는 구현 규칙으로 해석하지 않는다.

| 항목 | 30일 | 31일 |
|---|---:|---:|
| 정기 확인 × 송출표 최대 2개 | 1,728,000회 | 1,785,600회 |
| 미디어·사진·HEAD·추가 조회 여유, 하루 20,000회 | 600,000회 | 620,000회 |
| 합계 | **2,328,000회** | **2,405,600회** |
| 무료 10,000,000회 대비 | **23.28% 사용, 76.72% 여유** | **24.06% 사용, 75.94% 여유** |

R2 GET/HEAD/Range는 실제 작업 수로 계산. 공유 원본 한 개를 TV 100대가 각각 처음 내려받으면 다운로드 작업도 각 TV에 발생한다. 저장 원본 수와 다운로드 횟수는 별개다. 반복 재생은 검증된 로컬 캐시로 처리해 재생당 R2 GET을 만들지 않는다.

### 4-6. R2 Class A: 변경 작업 기준

5분 확인·하트비트·반복 오류마다 R2 상태 파일을 PUT하지 않는다. 아래는 운영 예시이며 실제 변경 횟수·분할 업로드 작업에 따라 달라진다.

| 하루 운영 가정 | 하루 Class A | 30일 | 31일 |
|---|---:|---:|---:|
| 업체 100개 + 공통 문서, 하루 1번씩 실제 게시 | 101회 | 3,030회 | 3,131회 |
| 새/교체 원본 하루 10개, 분할·검사 문서 포함 파일당 최대 20작업 | 200회 | 6,000회 | 6,200회 |
| 스크린샷 TV당 하루 1장 | 100회 | 3,000회 | 3,100회 |
| 메타 백업 하루 1개 | 1회 | 30회 | 31회 |
| 목록·재개·점검 등 여유 | 100회 | 3,000회 | 3,100회 |
| 예시 합계 | **502회** | **15,060회** | **15,562회** |

예시 30일 사용은 무료 1,000,000회의 약 1.51%. 실제 운영 목표 100,000회 이하를 별도로 둔다. 큰 파일의 파트가 많거나 게시·사진이 잦으면 예시를 초과하므로 재계산한다. 같은 영상 100업체 참조로 원본을 100번 PUT하지 않는다. R2 DeleteObject·AbortMultipartUpload의 무료 작업 분류와 D1 삭제 행 비용은 분리한다.

### 4-7. R2 저장 공간과 단계 보호

| 원본 보관 가정 | 영상만 계산 |
|---|---:|
| 왼쪽은 업체마다 18MB, 오른쪽 143MB는 모든 TV가 동일 원본 공유 | 18 × 100 + 143 = **1.943GB** |
| 양쪽 161MB가 업체마다 모두 서로 다름 | 161 × 100 = **16.1GB** |

실제 모든 right 파일의 합집합·예약·공지·교체 전후본·사진·검사 문서·백업·미완료 파트까지 확인한다. 1.943GB는 공유 조건의 예시이며 현재 계정의 실제 용량이 아니다. 10개 원본을 올리는 작업량 예시도 그 원본을 계속 보관할 수 있다는 뜻은 아니다.

| 사용·예약 포함 예상 공간 | 상태·행동 |
|---|---|
| 5GB 미만 | 정상, 현재 재고·신규 예상량 확인 |
| 5GB 이상 ~ 6GB 미만 | 관리자 경고, 증가 이유·불필요 파일 목록 표시 |
| 6GB 이상 ~ 7GB 미만 | 미완료 임시·오래된 사진·불필요 메타 백업을 안전하게 정리 |
| 7GB 이상 ~ 8GB 미만 | 일반 신규 대용량 미디어 업로드 제한, 필수 작은 제어·복구를 우선 |
| 8GB 이상 | 비상. 신규 미디어·선택 촬영·백업 중지, 원인 확인·기존 방송 유지 |

정확히 5/6/7/8GB이면 다음 보호 단계에 들어간다. 공식 무료 한도와 별개인 우리 보호선이다.

- 업로드 전에 실제 보관량 + 진행 중 예약량 + 신규 최대 크기로 예상 용량 판단. 완료 후에만 경고하는 방식 금지.
- 동시 업로드 공간은 D1 조건부 예약으로 중복 사용 방지. 예약·확인·해제의 행 비용을 기타 쓰기 예산에 포함.
- multipart의 미완료 파트와 일시적인 신구본도 계산. 실패/중단 정리 작업도 예산 내 수행.
- 모든 업체/편성의 참조를 확인. **현재 송출·예약·공지용 파일은 공간 확보를 위해 임의 삭제하지 않음.**
- 기존 정상 원본을 먼저 지워 새 교체본을 위한 공간을 만드는 방식 금지. 교체 중 임시 증가를 예약할 공간이 없으면 변경 대기.
- 사진은 기기당 최신 1장·전체 1GB 초기 예산. 새 사진 저장 성공 후 이전 사진 정리. 네이티브 PNG 실제 크기 실측.
- 메타 백업 최근 3개 기본, 영상 원본 전체 복제 금지. 필요한 삭제 이력은 백업 개수 정리로 유실하지 않음.
- 장부는 주기적으로 제한된 R2 조회와 대조. 계정의 다른 버킷·직접 업로드를 포함. 전체 스캔을 매 5분마다 실행하지 않음.
- 정리할 안전 파일이 없으면 업로드를 제한하고 부족 공간 표시. 보호된 정상 방송을 지우지 않음.
- 경고·업로드 제한은 계정 전체 초과 과금을 완전히 보장하는 장치가 아님. 다른 서비스도 사용하는 경우 전체 합계를 측정.

| D1 장애·한도 소진 | 마지막 정상 방송 유지, 정상 목록을 빈 목록으로 덮지 않음 | DB 오류/한도·조회 실패, 정상으로 위장 안 함 |
| R2 GET 실패 | 받은 파일 계속, 새 다운로드는 대기 | 필요한 파일 준비 지연 |
| Workers 장애·요청 한도 | 캐시 재생 유지, 재시도 조정 | 새 편성·명령 전달 지연 |
| 한 파일 고장 | 해당 파일 재시도·제외, 다른 파일·반대 화면 유지 | 부분 장애·파일 제외 |
| 한쪽 전부 고장 | 해당 화면 기본 이미지, 다른 화면 유지 | 해당 화면 전체 장애 |
| 일시적으로 빈/파손 응답 | 기존 정상 목록 보존 | 수신 검증 실패 |
| 완성된 정상 빈 목록 | 명시적인 삭제·정지 의미를 적용 | 빈 편성/기본 화면 |
| 사진 저장 실패 | 방송 유지, 기존 사진 보존 | HTTP 실패·촬영 저장 실패 |
| 서버 복구 | 최신 버전 한 번 확인, 받은 삭제·제외부터 적용 | 최신 편성 수신·준비·재생 단계 |
| 만료된 명령 | 실행 안 함 | 명령 만료 |
| 저장소 전체 삭제/처음 설치 후 오프라인 | 정상 파일이 없으면 기본 연결 안내 | 오프라인 재시작 보장 불가 |

서버 장애 중 새 파일을 못 받아도 재생 담당을 정지시키지 않는다. 우선순위는 이미 받은 삭제·업체 정지·유효 휴무/블랙 제어 → 준비된 정상 방송 → 최신 변경 확보 → 부가 기록이다. 공지 등 의도적 화면 제어는 기존 의미를 보존한다.

통신 실패는 한 담당자가 1분 → 5분 → 15분 → 최대 30분으로 늦추며 지터·서버 Retry-After를 준수한다. 네트워크 복구 신호는 확인 한 번으로 합친다. 확인된 일일 무료 한도 소진은 서버 안내와 UTC 초기화를 고려한다. 모든 서버 오류를 D1 한도 소진으로 단정하지 않는다.

서버가 복구되면 과거 목록을 차례대로 방송하지 않는다. 최신 목표를 조회하고 tombstone·선정·제어를 적용한 뒤 필요한 파일만 받는다. 이미 실행한 명령은 재실행하지 않고 만료 명령을 버린다.

**API 주소를 삭제하는 것과 새 Player의 정기 호출을 없애는 것은 다르다.** 전환 중 구버전·APP·CMS에 필요한 기존 주소는 호환 유지한다. 새 Player 안의 중복 확인 담당자를 없앤다.

## 7. 구현 상세와 기존 좋은 설계의 보존

### 7-1. APP과 기존 기능 유지

- MainActivity·설정 화면·Manifest·Gradle·APK 변경 없음.
- 기존 플레이어 최종 출처와 경로를 유지. 새 프로젝트 주소로 옮겨 기존 저장소를 잃는 방법을 기본으로 쓰지 않음.
- 기존 /api/app-config의 필드·주소 유지. 변경 없는 playerUrl에 매번 시각·토큰·버전 문자열을 넣지 않음.
- 설정 조회 장애를 ok:true, active:false로 위장하지 않음. 503 또는 ok:false로 APP의 마지막 정상 URL 분기를 이용.
- 업체 비활성·삭제는 플레이어의 정지 제어로 실제 적용하고 구버전 검정 화면 응답과 호환. APP의 안내 반환만으로 중지가 완료됐다고 판단하지 않음.
- 기존 리모컨 0 다섯 번·MENU/SETTINGS, 전체 화면·화면 유지·부팅 진입 동작 보존.
- 0213 로그인 정책 유지. 관리자 변경·명령·백업·복구 API는 서버 권한 확인.
- 웹 단독 플레이어·미리보기·진단 JSON·기존 통계도 회귀 시험.
- 지원되지 않는 TV 재부팅·전원 제어를 APP 새로고침이라고 위장하지 않음.

### 7-2. 저장·예산 구현 기준

- runtime_status: 기기별 최신 요약·활성 세대·sequence·정상/중요 저장 시각·UTC 일별 예산·명령/배포 결과. 필요한 최소 색인만 변경.
- error_samples: 최대 10개/TV/UTC일 기본, eventId 기본키·필요 조회 색인. 원문 제한과 현재 장애 요약은 별도.
- commands: commandId·대상 웹 설치/검증된 기기·createdAt·expiresAt·수신/시작/확인 결과. 실행 전 로컬 처리 기록, 같은 명령 재전송 중복 방지.
- publication/delete_ledger: 단조 증가 버전, 삭제 원장·선정·제어를 옛 백업·롤백으로 되돌리지 않음.
- storage_reservations: 동시 업로드 예약·완료·실패/정리 상태. 행 비용은 별도 기타 예산에 포함.
- 상세 쓰기와 상태 쓰기를 한 호출에서 함께 해도 행 비용은 각각 계산. 필요하면 D1 batch로 원자적 갱신.
- 중요 변화가 없는 regular 요청에서는 UPDATE·INSERT·DELETE·스키마 유지 작업 0회. 처음 등록·20분 도래·진짜 중요 변화만 예외.
- 이벤트와 정상 저장이 같은 요청이면 현재 요약 행 갱신을 합침. 새 정상 슬롯을 건너뛰거나 중요 사건을 두 번 저장하지 않음.
- 서버 조건부 갱신으로 중복 packetId/eventId, 낮은 sequence, 옛 세대, 동시 상태 쓰기를 처리.
- 정상 계측에 API당 장부 UPDATE를 추가하지 않음. 실제 rows_read/rows_written은 모든 SQL의 meta를 합산.
- 공용 보호 시 상세 원문·과거 정리·빠른 관리자 갱신부터 줄임. 현재 요약·복구·명령 결과와 정기 상태 몫 우선.
- 전체 요약의 크기는 실제 최대 편성으로 시험. 큰 문제 목록은 분할 조회하며 문제 항목을 잘라내고 정상이라고 표시하지 않음.
- 현재 장애는 비복구 상태로 유지, 영구 삭제/편성 해제는 대상 해제로 구분. 다른 영상 성공은 해당 파일 복구 증거가 아님.

### 7-3. 송출표 게시와 잘못된 빈 목록 방지

- 업체 불변 ID·게시 버전·완성 여부·현재 그룹·예약·공지·제어·삭제 버전을 함께 정의.
- 완성된 새 버전의 명시적인 빈 배열만 정상 빈 목록으로 인정. 401·503·파손 JSON·누락 필드·타임아웃은 삭제가 아님.
- D1은 편집 원본과 작은 공개 버전 포인터를 저장. R2는 고정 버전 송출표와 파일을 보관.
- 같은 버전이면 작은 응답만 반환. 매 정기 확인에 D1에서 전체 목록을 다시 만들지 않음.
- 오른쪽 공통 원본·선정 규칙은 공유하고, 통합 API가 업체별 허용 결과를 반환. 플레이어도 재확인.
- 파일 검사 목록은 별도 고정 문서로 두어 정기 답변을 작게 유지. 송출표가 커서 추가 읽기가 필요하면 그 작업량을 예산에 합산.
- R2 완성 송출표 저장 후 D1 공개 포인터 변경. 저장·게시 사이 실패는 작업 번호로 재개.
- 동시 편집은 revision 충돌 확인. 늦은 완료 작업이 최신 버전을 되돌리지 않음.
- 관리 작업·예약 시간 경과를 정기 스키마 보강·전체 R2 스캔의 이유로 사용하지 않음.
- 작은 무료 정기 작업 Worker가 미완료 배포·임시 파일·과거 오류를 나누어 처리. 추가 DO를 기본 의존성으로 만들지 않음.
- 새 저장 공간은 서버 장부에 먼저 예약. 동시 업로드의 공간 중복 사용을 막고 실패 시 반환.

### 7-4. 점진 재생과 변경 작업 취소

- 현재 목록 전체 준비를 목표로 하되, 일반 목록은 준비된 정상 파일부터 CMS 순서대로 재생.
- 최초에는 left 첫 파일과 right 첫 파일에 공정한 다운로드 기회. 기본 다운로드 동시 수는 1.
- 준비 파일이 하나면 반복, 없으면 캐시된 기본 화면. 부분 파일은 재생하지 않음.
- 기존 준비 파일은 재사용. 같은 파일 순서·표시 시간 변경은 다운로드 없이 적용.
- 명시된 동일 콘텐츠 교체 관계가 있는 이전 유효본만 새 버전 준비까지 임시 사용.
- 목록 위치만 같다고 삭제된 B를 새로운 D의 임시 대체로 사용하지 않음.
- 목록이 A→B→C에서 A→D→C→E로 바뀌고 B가 삭제되면, A·C를 재사용하고 B는 제외. D·E가 준비되는 대로 새 순서에 포함.
- 반드시 함께 표시해야 하는 묶음만 전체 준비 후 전환. 왼쪽 실패 때문에 오른쪽 정상 준비를 막지 않음.
- 더 최신 목록이 도착하면 이전 작업의 적용 권한 취소. 다운로드 완료 직전에 최신 필요 집합과 삭제 기록을 다시 확인.
- 삭제·대상 제외·정지 제어는 새 파일 준비를 기다리지 않고 우선 적용.

### 7-5. 캐시·검사·정전 복구

- Cache Storage는 미디어·실행 파일, IndexedDB는 준비 상태·목록·삭제·명령·오류 대기열. localStorage에는 작은 호환 식별값만 둠.
- 기존 캐시를 새 메타정보에 연결하여 재사용. 프로그램 버전이 바뀌었다고 미디어 전체를 다시 받지 않음.
- 임시 저장 → 크기·원본 검사 → 최종 파일 존재 확인 → ready 기록 순서. Cache와 IndexedDB를 하나의 원자적 저장이라고 가정하지 않음.
- 재시작 시 실제 파일과 ready 기록 대조. 파일 없는 ready는 철회.
- HTTP 200이어도 HTML·빈 파일·불완전 206·opaque 응답은 완전한 파일로 인정하지 않음.
- 현재 SHA-256-CHUNKS, 1MiB 구간, byteSize, hashes, revision 형식 유지. revision은 구간 정보 목록의 식별값이며 전체 파일의 단일 SHA-256과 혼동하지 않음.
- 검사 정보는 CMS 브라우저·관리 도구에서 만들고 TV에서 대조. 원본 없이 만든 자체 해시를 원본 일치 증거로 표시하지 않음.
- 큰 파일 전체를 서버 JS로 해시하거나 Base64로 localStorage에 저장하지 않음. 매 재생마다 전체 검사 반복하지 않음.
- 기본 재생은 검증된 캐시 Blob 경로를 유지. Range 최적화는 전체 200 캐시·정확한 206/416·외부 통신 차단을 같은 TV에서 확인한 경우만 적용.
- 파일 개수 20개 제한으로 필요한 현재·예약·공지 파일을 잘라내지 않음.
- 용량은 현재·예약·공지의 고유 파일 합 + 저장 중 최대 파일 두 배 + 프로그램·로그·여유로 계산.
- 정상 현재 파일을 단순히 오래됐다는 이유로 지우지 않음. 새 준비·예약·공지에 필요한 파일을 우선 보존.
- 손상된 파일만 복구. 캐시 전체 초기화는 정상 업데이트·자동 오류 복구에 사용하지 않음.
- storage.estimate/persist 지원·거절·미지원을 표시하고 TV별 실제 저장 여유 확인.
- 처음 실행 파일을 못 받았거나 모든 웹 저장소가 삭제된 경우, 오프라인 재시작을 보장하지 않음.

### 7-6. 삭제 원장과 백업

- 영구 삭제는 assetId와 버전을 삭제 원장에 먼저 기록하고 현재·예약·복구 목록에서 제외.
- 물리 파일 삭제 실패·다운로드 완료·옛 스냅샷·이전 묶음 복구가 삭제 원장을 무시하지 못하게 함.
- 다른 살아 있는 콘텐츠가 같은 원본을 공유하면 원본 파일은 유지하되 삭제한 assetId는 재생 금지.
- 오래된 백업을 복원해도 삭제·정지 제어 버전을 과거로 되돌리지 않음.
- 새로 등록하는 콘텐츠는 명시적인 새 assetId를 사용. 오래된 assetId를 몰래 복구하지 않음.
- 백업은 업체·APP ID·URL·기기 대응·파일 버전·검사 정보·선정·그룹·시간표·공지·휴무·설정·삭제·스키마 포함.
- DB 조회 일부 실패·degraded 결과는 완전 백업으로 저장하지 않음.
- 복원은 미리 검사하고 새 게시 버전 발급. 복원 후 대상·예약·정지 제어·기기 연결 확인.
- 이미 R2에서 삭제한 원본은 메타 백업만으로 복구되지 않음. 재업로드 필요 표시.
- 롤백용 이전 플레이어도 삭제·제어 버전을 이해하는 호환본을 사용.

### 7-7. 원격 프로그램 전환

- 배포 전 실제 APP·WebView·현재 최종 URL·playerBuild·SW 경로·저장 기능을 읽기 전용 진단으로 확인.
- 새 HTML·JS·CSS·SW·기본 이미지를 하나의 release로 정의하고 모두 준비한 뒤 전환.
- 기존 sw.js 경로와 scope를 이어받아 설치·업데이트·활성화·실제 controller 변경 확인.
- version.json만 바뀌거나 reload만 했다고 새 코드 활성화 완료로 인정하지 않음.
- 현재 페이지가 쓰는 구 실행 파일을 새 SW 활성화 중 지우지 않음. 이전 호환 실행 파일과 정상 미디어 캐시 보존.
- skipWaiting·clients.claim은 준비 확인 후 같은 APP에서 시험. 옛 문서와 새 파일이 섞이지 않게 함.
- 기능 적용 대상은 웹 설치 ID로 구분. 같은 APP ID의 여러 TV가 한 기기로 취급되지 않게 함.
- 기능이 부족한 TV는 기존 호환 버전을 유지하고 미지원 이유 표시. OS·WebView 업데이트를 배포 필수 조건으로 요구하지 않음.
- 안정된 playerUrl 유지. nativeReload 같은 임시 값은 문서 캐시 처리에 반영하되 업체·APP ID는 무시하지 않음.
- 실패 시 같은 출처의 이전 호환 release로 복귀. 미디어 캐시·삭제 이력은 지우지 않음.
- 새 build 실제 실행과 첫 재생 확인이 있어야 업데이트 완료.

### 7-8. 공지·휴무·시간·기기 자원

- 우선순위 출발점: 업체 정지·삭제 → 수동 검정 화면/휴무 → 유효 공지 → 높은 우선순위 예약 → 기본 편성 → 기본 화면.
- 기존 긴급 공지 의미와 충돌하면 현행 기능 대조표로 최종 결정. 판단 실패를 OFF로 처리하지 않음.
- 시간표·기간·공지 종료는 저장 정보와 서버 시간 보정으로 로컬 적용. 자정·요일·동점 우선순위·재부팅 후 시계 오차 시험.
- 시계가 불확실하면 시간 상태를 표시하고 날짜 제한 파일은 보류·기본 편성 사용. 통신 24시간 경과를 이유로 right 전체를 중지하지 않음.
- 공지의 once/daily/interval/command 반복 규칙과 종료 후 기본 영상 복귀 보존.
- QR·텍스트 렌더러와 필수 라이브러리는 자체 포함하여 외부 서비스 연결에 의존하지 않음.
- 좌우 각각 활성 영상·이미지 하나. 전환 시 src·Blob URL·디코더 정리.
- 전체 화면 영상 공지는 좌우 영상 자원을 먼저 해제하여 세 영상 동시 디코딩을 기본으로 만들지 않음.
- 지원 프로필은 기존 H.264 MP4·30fps 이하 등 현장 기준. 무료 Worker에 영상 변환을 맡기지 않음.
- 실제 최대 파일과 TV로 72시간 이상 메모리·재생·캡처 부하 확인.
- JS가 완전히 멈추면 같은 JS 감시가 스스로 복구할 수 있다고 주장하지 않음.

### 7-9. 공개 파일·업로드·예산 보호

- 광고 파일과 사진·오류·메타 백업·기기 설정을 분리. 공개 R2의 폴더 이름만으로 비공개라고 하지 않음.
- 필요하면 관리 자료용 비공개 R2와 바인딩을 사용. 기존 APP 업로드 주소·형식은 유지하고 서버가 저장 위치를 선택.
- 관리자 읽기·변경·삭제·명령에 권한 확인. 기존 native 업로드에 새 필수 인증 헤더를 강제하지 않음.
- URL은 승인 HTTPS 출처로 제한, 공지 입력·외부 iframe·임의 JS·CSP·출력 인코딩 확인.
- 미디어 도메인의 CORS와 파일 읽기·크기·Range 헤더를 실제 확인. no-cors로 읽기 불가를 숨기지 않음.
- 기존 운영용 미디어 도메인 사용 우선. 없으면 기존 미디어 API와 캐시를 사용하고 요청량 합산. r2.dev를 운영 필수 경로로 삼지 않음.
- 관리자 큰 파일은 제한된 직접 업로드·분할 전송 등으로 Worker의 CPU·메모리·100MB 요청 제한을 피함. 서명·분할·최종 확인 작업도 예산 포함.
- R2PutOptions의 단일 SHA-256 검사와 기존 구간 검사 revision을 혼동하지 않음. multipart ETag를 전체 파일 SHA-256이라고 해석하지 않음.
- 정적 프로그램 파일은 불필요한 Functions 처리에서 제외. 기존 middleware 때문에 모든 파일 요청이 동적 예산을 쓰지 않게 함.
- 일반 실패는 1분 → 5분 → 15분 → 최대 30분으로 늦춤. 한 통신 담당자가 재시도를 조정하고 회선 복구 시 한 번 빠르게 확인.
- 실제 일일 한도 소진은 서버 안내와 한국 시간 오전 9시 초기화에 맞춰 대기. 다른 실패를 무조건 D1 초과라고 단정하지 않음.
- 새 정기·추가 요청 예산은 4-2절의 300+10+20+40 모델을 사용. 실제 계정 합계로 검증.
- 4-2절의 48,800회/일 예외 모델은 native 30분·사전 요청 없음 가정. 재부팅으로 예산 초기화하지 않음.
- 부가 기록이 하루 정기 확인 몫을 먼저 써버리지 못하게 함. 예산 보호 시 갱신 지연·축약 표시.
- 정상 로그·반복 오류·빠른 관리자 조회·대량 정리부터 줄이고 기본 확인·복구 우선.
- 실제 계정 전체가 소진되면 서버 기능은 제한됨. 경고 화면을 비용 자동 차단 장치라고 주장하지 않음.

### 7-10. 처음 원격 교체하는 순서

1. 현재 최종 Player URL·SW 경로·기기별 playerBuild·현재 기능을 읽기 전용으로 확인.

3. 같은 Player 출처·sw.js 경로에 새 SW와 호환 전환용 release 준비. 처음에는 구버전의 version.json 확인을 전환 신호로 사용.
4. 구 SW가 실제로 교체되고 새 HTML/JS 묶음을 사용했는지 확인. reload만 했다고 완료 처리하지 않음.
5. 새 Player 한 개만 활성화, 옛 정기 담당자 정리, 정상 미디어·삭제 기록 이행.
6. 새 build 실행·좌우 첫 재생·새 sync 요청 패턴을 확인하고 적용 완료 처리.
7. 실패 시 같은 출처의 이전 호환 release로 복귀. 삭제·선정·정지 제어를 이해하지 못하는 옛 구현으로 무조건 롤백하지 않음.

이미 가진 SW 코드가 새 배포를 자동 확인하는지 같은 APP에서 시험한다. 교체가 안 된 TV는 업데이트 미확인으로 표시한다. 현장 방문·APP 재설치 없이 전환에 성공하지 못한 TV를 성공 기기 수에 포함하지 않는다.

수동 전체 초기화 기능은 보존한다. 초기화로 웹 저장소가 삭제되면 서버 삭제 원장·최신 정상 목록을 다시 확인한 뒤 광고를 시작한다. 정상 업데이트에서 native clearWebViewCache를 호출하여 저장소 전체 삭제를 유발하지 않는다.

### 7-11. 기존 APP과 스크린샷을 연결하는 정확한 규칙

처리 순서: 요청 저장 → 다음 sync에서 명령 수신 → 기존 captureScreenshot 호출 → 사진 업로드 → R2·D1 저장 확인 → CMS 결과 표시.

- 기존 APP은 captureScreenshot(String payloadJson)의 전달 내용을 사용하지 않는다. 새 commandId를 전달해도 APP이 사진에 붙여 줄 것이라고 가정하지 않는다.
- POST /api/screenshots와 multipart의 file·store·deviceId, PNG 형식을 그대로 받는다. native 캡처 ID를 웹에 알려 주는 새 bridge 함수도 요구하지 않는다.
- 업체 ID·APP ID·웹 설치 ID·native 캡처 ID를 각각 보관. 확인된 1:1 대응이 있으면 사용하되 물리 기기 인증으로 과장하지 않는다.
- 대응이 없으면 업체에 활성 TV 한 대·미완료 요청 하나일 때만 추정하고 추정임을 표시. 같은 APP ID의 TV 여러 대나 오래된 사진은 임의 기기·새 요청의 성공으로 연결하지 않는다.
- TV당 촬영 요청 한 개만 진행. 이전 요청의 지연 업로드가 새 요청에 섞일 수 있으면 요청 연결 미확인으로 처리. 업체 단위 UPDATE로 다른 TV까지 완료시키지 않는다.
- 요청 시각·명령 수신 시각·서버 사진 수신 시각을 구분. 기존 APP은 실제 촬영 시각을 보고하지 않으므로 서버 수신 시각을 촬영 시각이라고 표시하지 않는다.
- 명령 호출만 됐으면 사진 업로드 대기. 사진과 주소 기록 모두 저장됐을 때 사진 수신 완료. 예전 사진만 있으면 예전 사진·수신 시각을 유지한다.
- 기존 APP은 응답 JSON보다 HTTP 2xx 여부로 성공을 판단한다. R2 저장 또는 D1 기록 실패는 비정상 HTTP 상태로 반환하며 ok:true·saved:false로 성공을 위장하지 않는다.
- R2만 저장되고 D1이 실패한 경우 기존 사진을 보존하고 새 고아 사진을 안전 정리 대상으로 기록. 재시도·정리 비용을 별도 예산에 포함한다.
- PixelCopy 및 WebView.draw 대체 촬영이 실제 좌우 영상을 담는지 같은 APP·TV로 시험. 검은 영상 캡처나 APP 안의 PNG 압축 부하는 CMS 수정만으로 해결됐다고 주장하지 않는다. APP 무변경 범위에서 해결되지 않는 기기는 미확인/제약으로 표시한다.
- 기기당 최신 1장·전체 1GB는 초기 사진 예산. 새 사진의 R2·D1 저장 성공 후 이전 사진을 정리하고 실제 PNG 크기를 측정한다.

### 7-12. right 선정과 콘텐츠 식별

| 선정 정보 | 송출 결과 |
|---|---|
| 명시적인 all | 전체 업체 허용 |
| selected + 확인된 해당 업체 | 해당 업체만 허용 |
| selected + 빈 목록 | 어떤 업체도 허용하지 않음 |
| 업체 미확인·불일치·선정 정보 누락/파손 | 새 미검증 콘텐츠 제외, 확인 대기 |

목록 API·공통 right 스냅샷·그룹·예약·미리보기·진단에 같은 필터를 적용한다. 오프라인에서는 이미 확인한 정상 허용 목록을 사용하고, 새 제외·삭제를 받은 즉시 해당 광고를 멈춘다. 대체 파일 준비를 기다리며 제외된 광고를 유지하지 않는다.

assetId는 업무상 콘텐츠 ID, assetVersion은 그 콘텐츠의 버전, contentHash/R2 key는 공유 원본 식별이다. 서로 다른 assetId가 같은 원본을 참조할 수 있다. 한 assetId 삭제가 살아 있는 다른 참조의 원본 삭제로 이어지지 않게 한다. 순서·표시시간 변경은 콘텐츠 바이트 버전을 새로 만들지 않는다.

시간·한도 소진 시험은 모의 실패로 하고 실제 무료 계정을 일부러 소진하지 않는다. 정상일뿐 아니라 원본 교체일·사진 다수·오류 폭주·서버 복구일·신구 버전 공존일을 따로 측정한다. 해당 일에 목표를 못 지키면 원인·최대량·보호 동작을 보고하고 보완 후 확대한다.

## 9. 실제 R2·D1 운영 위험과 확인 자료

| 예상 위험 | 쉬운 뜻 | 운영 대응 |
|---|---|---|
| 서로 다른 영상·교체본 증가 | 창고에 같은 줄 알았던 영상이 여러 개 쌓임 | 실제 고유 원본 합·예약·임시 파트까지 계산, 5/6/7/8GB 보호 |
| 오류마다 원문 쓰기 | 공책에 같은 고장 이야기를 수백 번 적음 | 사건별 합산·표본 제한·현재 상태 우선 |
| 5분마다 상태 쓰기 | 확인할 때마다 공책도 고침 | 20분 저장 외 read-only regular 쓰기 0행과 하루 정상 72회 검증 |
| CMS 접속 표시 지연 | 5분 통신에 성공해도 공책은 20분 전 자료일 수 있음 | 선택 A로 명시·자료 시각 표시. 30분 확인 경고를 전원 종료로 단정하지 않음 |
| 작은 요청의 무거운 계산 | 전화 횟수는 적어도 서버가 한 번에 너무 오래 계산함 | CPU 10ms·p99·exceededCpu 시험, 게시/검사/정리를 regular 밖에서 수행 |
| 색인·예산 장부 추가 | 한 줄 쓰는 줄 알았는데 여러 줄을 고침 | 모든 rows_written 측정, 3행 가정 초과 시 설계 보완 |
| 잦은 자동 사진·미디어 재다운로드 | 영상·사진을 계속 새로 받아 작업량 증가 | 요청 기반 사진, 최신 1장, 재생은 정상 캐시 사용 |
| 다른 프로젝트 사용·직접 업로드 | 우리 장부 밖에서도 같은 창고·공책 한도를 사용 | 계정 전체 합산·장부 대조·추가 작업 제한 |

| R2 무료 제공량 초과 | 창고/파일 작업에 과금 가능 | 경고보다 먼저 신규 용량·작업 예산 확인 |
| 계속 오프라인 | 새 삭제·선정을 TV가 못 들음 | 받은 정책 계속, 복구 후 최신 정책부터 |
