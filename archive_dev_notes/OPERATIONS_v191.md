# LocalVision Player 1.9.1 배포와 운영

대상: Player 1.9.1 / CMS 2.1.0. 이번 수정 기준: Player 1.9.0. CMS 2.1.0은 변경하지 않았습니다.

## 이번 페이지 로딩 수정
사용자가 제공한 HTTP 검사에서는 HTML·JS·버전 파일의 응답 코드와 형식이 정상이었습니다. 이것만으로 브라우저의 서비스 워커 캐시 경로까지 확인되지는 않습니다.

1.9.0은 `index.html`을 사전 저장하고, 페이지를 열 때 저장된 Response를 그대로 반환했습니다. Cloudflare Pages는 HTML 주소를 정규 주소로 리디렉션할 수 있습니다. 리디렉션 이력이 있는 Response를 특정 페이지 이동 요청에 재사용하면 Fetch 규칙에 따라 네트워크 오류가 됩니다. 이전 시험은 이 이력이 없는 Response만 사용하여 이 조건을 놓쳤습니다.

1.9.1은 저장 단계와 페이지 응답 단계에서 읽을 수 있는 정상 HTML로 새 Response를 만듭니다. 캐시 접근이 실패하면 서버 HTML로 복구를 시도하고, 그것도 실패하면 연결 복구 안내를 표시합니다. 새 서비스 워커가 활성화되면 이전 앱 화면 캐시만 정리합니다. 미디어 파일 캐시와 플레이리스트 저장 기록은 유지합니다.

이 결함은 PC와 기존 사용 기기 사이의 차이를 설명할 수 있는 후보입니다. 실제 장애 기기의 원인 확정에는 아래 기기 확인이 필요합니다.

근거: [Cloudflare Pages의 HTML 리디렉션](https://developers.cloudflare.com/pages/configuration/serving-pages/), [Fetch 표준의 서비스 워커 응답 검사](https://fetch.spec.whatwg.org/#http-fetch).

## 먼저 읽어 주세요
이번 패키지는 웹 Player와 Cloudflare CMS 소스입니다. Android APK를 변경하거나 실제 TV에서 인증한 버전이 아닙니다. 자동화 시험 결과는 TEST_REPORT.md에 기록합니다. 실제 장비의 좌우 동시 디코딩 능력, 운영 Cloudflare 환경, 전원·HDMI·WebView 렌더링은 별도로 검증해야 합니다.

## 설치 순서
1. 기존 저장소의 운영 커밋과 기존 ZIP을 보관합니다. 기존 Cloudflare Pages/D1/R2 설정도 기록합니다.
2. 현재 CMS가 2.1.0이면 CMS 배포는 생략하고 4번으로 진행합니다. CMS 2.1.0을 처음 설치한다면 이전에 전달한 CMS ZIP의 최상위 버전 폴더 **안의 내용물**을 기존 CMS GitHub 저장소 루트에 반영합니다. GitHub에 ZIP 자체를 업로드하는 방식이 아닙니다. 기존 Cloudflare GitHub 연결을 유지합니다.
3. Cloudflare Pages 빌드 명령 `npm run build`, 출력 폴더 `dist`, 저장소 루트의 `functions`, D1 `DB`, R2 `MEDIA` 및 기존 환경 변수/R2_PUBLIC_BASE를 유지합니다. GitHub Pages 단독으로 CMS API가 작동하지 않습니다. dist도 새 버전으로 동봉했지만 저장소 연결 빌드를 권합니다.
4. Player ZIP의 최상위 버전 폴더 안 내용물 전체를 기존 Player 저장소 루트에 반영합니다. `_headers`, `sw.js`, `index.html`, `app.js`, `integrity.js`, `playlist-store.js`, `runtime.js`를 함께 반영해야 합니다. Player는 기존 정적 사이트의 배포 루트/연결 설정을 유지합니다.
5. Cloudflare 배포 완료 후 `/version.json`의 version이 `1.9.1`인지 확인합니다. 기존 매장 URL/API/store 설정을 유지하고, 문제가 있었던 장비 한 대부터 온라인 상태에서 앱/브라우저를 완전히 닫고 다시 엽니다. 새 서비스 워커 설치에는 연결이 필요합니다. 이전 오류 화면이 남으면 온라인 상태에서 30~60초 뒤 한 번 더 닫고 열어 보세요. 업데이트 적용 시점은 WebView/브라우저마다 다르므로 이 절차만으로 적용을 보장하지 않습니다. 실제 Player 화면 또는 CMS 기기 보고의 Player 버전도 확인합니다.
6. CMS의 ‘송출 진단 · 전체 기기’ 또는 `/playback-health.html`에서 매장을 선택하고 단계별 상태를 확인합니다.

## 기기별 차이가 계속될 때
앱의 ‘데이터 삭제’, 전체 사이트 데이터 삭제, 공장 초기화는 먼저 하지 마세요. 저장된 영상과 설정을 잃을 수 있습니다. 원인 구분에는 다음 결과가 필요합니다.

| 비교 | 확인할 내용 |
| --- | --- |
| 같은 실패 기기: 브라우저 / LocalVision 앱 | 동일한 매장 URL을 각각 열어 결과와 오류 문구를 기록합니다. 브라우저만 되면 앱·WebView 쪽 조사가 우선입니다. |
| 같은 실패 PC: 일반 창 / 시크릿 창 | 일반 창만 실패하면 기존 저장 상태나 확장 기능 등의 차이를 조사합니다. 캐시 결함 하나로 단정하지 않습니다. |
| 같은 기기: 매장 네트워크 / 휴대폰 핫스팟 | 브라우저도 실패한다면 연결 경로에 따라 달라지는지 확인합니다. 핫스팟에서만 되면 매장 DNS·라우터·필터 경로 조사가 우선입니다. |

실제 장비의 모델, 운영체제, Chrome/Android System WebView 버전, 전체 URL, 오류 문구와 발생 시간을 함께 기록합니다. `ERR_FAILED`는 원인이 하나로 정해지는 오류 코드가 아닙니다. 새 Player가 시작되기 전 실패하면 Player의 CMS 로그도 전송할 수 없습니다.

앱에서만 계속 실패하면 Android 앱 소스 또는 앱의 WebView 오류 로그가 필요합니다. 이번 ZIP에는 APK 수정이 포함되어 있지 않습니다. 새 URL 파라미터를 붙이는 것만으로 기존 서비스 워커를 해제할 수 있다고 가정하지 마세요.

파일 준비를 생략하는 `activateWhenCached=0`, 직접 영상 재생을 선택하는 `videoMode` 등 예전 우회 설정에 관계없이 이번 버전의 기본 플레이리스트는 검증된 캐시를 사용합니다. 일정 확인·하트비트 등 기존 URL의 명시적 간격은 유지합니다.

## 기존 업로드 파일: 한 번만 원본 검증 정보 생성
새로 업로드하는 콘텐츠는 CMS가 자동으로 검증 정보를 만듭니다. 이미 올려 둔 파일은 다음 작업이 필요합니다.

1. 송출 진단에서 매장을 선택합니다.
2. **기존 파일 원본 검증 정보 생성**을 누릅니다.
3. 창을 열어 두고 완료 결과를 확인합니다. 매장 콘텐츠와 공통 우측 광고를 최대 20개씩, 한 파일씩 처리합니다. 남은 파일이 있으면 다시 누릅니다.
4. 중단·연결 실패 시 재실행하면 이미 기록된 파일은 재처리하지 않습니다. 공통 광고는 다른 매장에서도 동일 정보를 재사용합니다.
5. TV는 다음 정기 목록 확인 때 원본 대조 정보를 받습니다. 이 작업은 원본 미디어를 재인코딩하거나 삭제하지 않습니다.

‘원본 대조 미완료’는 원본 해시가 아직 없다는 뜻입니다. 해당 파일은 로컬 내용의 기준값을 생성하고 이후 실행에서 비교하지만, 최초 다운로드가 서버 원본과 같았다고 보증하지 않습니다. 신규/정보 생성 완료 파일만 ‘원본 SHA-256 대조’로 집계합니다. 과거 snapshotFetch=1 URL을 사용한다면 스냅샷 갱신 실패 여부도 확인하세요. 기본 player-state 경로는 D1의 검증 정보를 읽습니다.

## 검증 방식과 적용 규칙
- 서버와 기기는 파일을 **1MiB 구간별 SHA-256**으로 비교합니다. `revision`은 구간 해시 목록과 파일 크기로 만든 SHA-256 식별값입니다. 일반 도구의 ‘파일 전체 SHA-256’ 값과는 다른 규격입니다.
- 한 파일 최대 1GiB, 최대 1,024개 구간입니다. 업로드 자체의 Cloudflare 요금제/요청 크기 제한은 이 한도와 별개입니다.
- 새 파일은 응답을 확보한 뒤 실제 크기와 구간별 해시를 검사하고, 성공한 경우에만 정식 캐시에 넣습니다. 한 번에 전체 파일의 ArrayBuffer를 만들지 않습니다. Blob의 실제 저장/메모리 사용은 WebView 구현에 따릅니다.
- 동일 실행에서 검증을 마친 파일은 재생 때마다 전부 해시 계산하지 않습니다. 재시작 후 최초 사용 시 다시 검사합니다. 재생 완료/첫 화면 감시는 별도로 유지합니다.
- 캐시 손상은 해당 파일만 다시 받습니다. 다운로드/검증은 최대 2회 시도 후 준비 실패로 남기고 현재 송출을 유지합니다. 반복 폴링 때 다시 시도할 수 있습니다.
- 새 콘텐츠 리비전은 별도 캐시 주소로 관리하여 이전 정상본을 덮어쓰지 않습니다.
- 새 목록·스케줄·이전 목록을 하나의 저장 기록으로 커밋한 뒤 화면에 적용합니다. 저장 공간 부족으로 이 기록을 남기지 못하면 새 목록을 적용하지 않습니다. 기본적으로 현재 목록과 이전 저장본을 보호합니다.
- 재시작 시 현재 기록에 필요한 파일이 누락되어 있고 이전 기록의 파일은 모두 있으면 이전 저장본으로 복원합니다. 이때도 각 파일의 검증은 재생 준비 시 수행됩니다. 이전본의 모든 영상이 실제 하드웨어에서 정상 디코드됐다는 인증은 아닙니다.
- 왼쪽만 변경되면 오른쪽을 다시 시작하지 않습니다. 두 목록이 함께 바뀌면 모두 준비된 뒤 적용합니다. 좌우의 프레임 단위 동기 재생 기능은 아닙니다.
- 공지 기능은 기존 흐름을 유지합니다. 공지 원본의 SHA-256 등록은 이번 CMS 기본 콘텐츠 업로드 범위에 포함하지 않았습니다.

## 다음 시간대 사전 준비
앞으로 24시간 안에 현재 그룹과 다른 그룹으로 바뀌는 가장 가까운 시점을 찾고, 그 목록 하나를 미리 준비합니다. 모든 미래 그룹을 무제한 다운로드하지 않습니다. 준비 완료 전에는 현재 송출을 유지합니다.

시간대 전환이 임박해 실제 적용이 필요하면 사전 준비를 취소하고 적용 경로가 우선합니다. 정상 재생 중인 검증 완료 파일은 사전 다운로드 대기열 뒤에 묶이지 않습니다. 사전 준비가 실패하면 사유를 표시하고 재시도 간격을 둡니다. 자정을 넘는 예약은 시작 요일 기준으로 CMS와 Player가 동일하게 해석합니다.

캐시 예산 기본값은 기존과 동일한 1GB(`cacheBudgetMB`)입니다. 현재+이전+다음 목록을 동시에 보관할 여유가 없으면 이전 정상 송출을 지키면서 새 준비를 중단합니다. 파일이 크다면 업로드 전에 경량화하거나 현장 저장 용량에 맞게 예산을 조정하세요. 저장소가 부족하다고 정상 송출본을 자동 삭제하지 않습니다.

## CMS 상태 읽는 방법
- 다운로드: 파일 수신 중
- 파일 검증: 원본 구간 해시/크기 비교 중
- 준비 완료: 목록에 필요한 파일 확보·검사 완료
- 목록 적용 완료: 기기의 적용 기록 저장 및 목록 교체 완료
- 좌우 ‘영상 재생/이미지 표시’: 각 화면의 실제 진행 보고
- 준비 중단: 새 목록은 적용하지 못했으며 기존 송출 상태를 별도로 확인

‘준비 완료’나 ‘목록 적용 완료’가 TV 패널/HDMI 출력 정상 인증은 아닙니다. 원본과 똑같은 파일이어도 코덱·디코더·메모리·원본 손상 문제로 재생은 실패할 수 있습니다. 자동 트랜스코딩, 전체 영상 디코드 검사, Android 네이티브 저장/감시 기능은 이번 업데이트 범위에 없습니다.

## 현장 검증과 운영
문제가 있었던 실제 장비에서 (1) 좌우 문제 영상 동시 재생, (2) 이미지 다수 전환, (3) 인터넷 차단/재연결, (4) 새 목록 다운로드 중 전원 재시작, (5) 다음 시간대 오프라인 전환, (6) 공지·휴무 복귀를 확인합니다. 실제 장비에서 72시간 운전 후 다른 매장으로 확대하세요. 기기별 고유 deviceId를 사용하고 복제하지 않습니다.

일반 refresh는 캐시와 저장 기록을 보존합니다. 명시적 강제 캐시 삭제는 이전 복구본까지 제거하므로 유지보수 중에만 사용합니다. 장기 로그는 기존 최대 1,500건/약 1.8MB 큐 정책을 유지합니다.

새 asset_integrity 테이블은 첫 쓰기에 생성합니다. 조회 API에서 스키마를 만들지 않습니다. 기존 원본 데이터나 업로드 파일을 일괄 삭제하지 않습니다. 관리자가 선행 생성할 경우 database/migration-v210-asset-integrity.sql만 사용하세요. 기존 schema.sql로 운영 DB를 초기화하지 마세요.

기존 CMS의 관리 접근 구조를 유지한 패키지입니다. 이 업데이트가 관리자 인증/보안 감사까지 완료했다는 뜻은 아닙니다. 기존에 사용하는 관리 접근 제한과 운영 계정 설정을 유지해야 합니다.

## 롤백
롤백이 필요하면 현장에서 정상 동작을 확인한 이전 CMS/Player 커밋으로 되돌려 재배포합니다. 페이지 캐시 결함이 있는 Player 1.9.0으로 되돌리면 같은 오류가 다시 나타날 수 있습니다. 새 D1 테이블을 삭제할 필요는 없습니다. 기존 v1-8-0 캐시 키와 이전 형식의 저장 목록도 유지합니다. 새 원본 검증 기능을 유지하는 현재 조합은 CMS 2.1.0 + Player 1.9.1입니다.
